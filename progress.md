# DTP — save point (reviewed 2026-09-23, night)

## November 9: a reservation's party must match its claim ([#145](https://github.com/runquik/direct-trade-protocol/issues/145))

The owner chose option 1 on November 4, for `inventory@2` and `flow@1` alike. A `reserve` on an existing `reservation_id` tops up the claim only when it names the same party; any other party, or `null` against a party, is `invalid`. A `release` or `fulfill` must name the claim's party, checked after the claim is found at its position and before the quantity. The reference reducers and both interop readers change the same way. The fixtures' existing release and fulfill operations now name their claim's party, and new cases pin a same-party top-up and each refused mismatch; the contract digests are unchanged. Builders: a host that matched claims by `reservation_id` alone now disagrees with the fixtures. It changed a packed entry after the `0.2.1-dev.1` boundary the November 8 entry names; #182 corrects that boundary (#181).

## November 7: an `inventory@2` ledger opens only under its product's policy ([#130](https://github.com/runquik/direct-trade-protocol/issues/130))

The owner chose option 1. `inventory.open` let the caller name any policy it could write, so a member with read-only access to a product could open the company's one ledger for it elsewhere and lock the product's own compartment out. The live path now refuses a `policy_id` other than the product record's policy with `403 forbidden`, after the product lookup and before the `409` for an existing ledger; the write check falls on the product's policy. Snapshot import refuses a ledger opened under another policy with `invalid_snapshot`. ## November 7: a snapshot carries owned state only ([#107](https://github.com/runquik/direct-trade-protocol/issues/107))

The owner chose option 2 on November 2. `buildSnapshot` no longer emits `remote_authorities`, so `snapshot_hash` depends only on what migrates, and a refresh of a counterparty's authority during the migration window no longer forces a new prepare. `validateSnapshot` requires exactly the nine owned-state members and refuses any other shape with `invalid_snapshot`; SPEC v0.4 section 8 lists them. `snapshot-import.json` is regenerated (every hash moves) with a new reject case `carries-remote-authorities`; regression test `tests/v04/snapshot-owned-only.test.ts`. ## November 7: membership revocation ends policy grants ([#98](https://github.com/runquik/direct-trade-protocol/issues/98))

A grant now counts only when the policy revision carrying it was signed after the person's latest `membership.revoke` in the company, so re-admitting a person no longer restores grants that no steward re-signed. A revocation signed before a newer granting revision is refused `409 conflict`, and a policy command signed at or before the grantee's latest revocation is refused `400 invalid`. The rule is derived from signed history only: no new state field and no snapshot format change. New vectors `spec/vectors/membership-revocation.json` (11 scenarios) and `sdk/tests/v04/membership-revocation.test.ts`, 6 of which fail without the fix. SPEC sections 3 and 4 and the builder baseline say so. Under the November 5 existence rule (#89), a re-admitted person's write is answered `404`.

## November 7: records are numbered per organization ([#71](https://github.com/runquik/direct-trade-protocol/issues/71))

The owner chose option (b). Every record's `seq` came from one host-wide counter, so the gap between two of a company's own `seq` values counted every other company's writes on the host. Each organization now has its own counter; a store without one continues after the company's highest existing `seq`. A snapshot numbers its records 1 to n and an import starts the company's own sequence, so staged imports reserve no shared capacity. An exhausted company sequence refuses the write `507 capacity`. SPEC section 6 ("Record sequence") and the section 8 capacity row state it. `tests/v04/record-seq.test.ts` replaces gap test #70. Builders: do not read meaning into `seq` across companies.

## November 7: a key that left the company's control no longer blocks import ([#137](https://github.com/runquik/direct-trade-protocol/issues/137))

The owner chose A1, B1 and C on November 4. At import, only a key that can still act for the company (a person's current key, an active installation's key) must be free at the destination; a retired key or a revoked installation's key is historical and does not refuse the import, though keys still may not alias inside the snapshot. A person the destination holds with another key history is kept as the destination holds it when the person is not a controller, active member or pending invitee; otherwise the import is refused `409 conflict`, naming the person and the remedy. Every key-collision refusal names the person or installation. SPEC sections 3 and 8 state the rules; new vectors `spec/vectors/snapshot-key-collision.json` (3 import, 4 conflict). `tests/v04/migration-key-squat.test.ts` replaces gap test #138.

## November 6: a Core-1 signed body nests at most 48 levels ([#149](https://github.com/runquik/direct-trade-protocol/issues/149))

## November 6: the observation window is an exact inequality ([#144](https://github.com/runquik/direct-trade-protocol/issues/144))

The owner chose option A on November 4: keep the reference window. ## October 23: a string value may not contain U+0000 ([#95](https://github.com/runquik/direct-trade-protocol/issues/95))

## October 23: the wallet signs only over the head it holds ([#83](https://github.com/runquik/direct-trade-protocol/issues/83))

The owner chose option 1 on October 22. A relying party advances its person checkpoint to the resolved head inside a person operation the owner's operational quorum signed, so a hostile former resolver could push that checkpoint out of reach of every owner-signed log by getting the wallet to sign one resolution over a fabricated head, and then block the owner's move as `behind` or `conflict`. The wallet now MUST NOT sign unless the resolution names its identity and its `head_digest` is the head of the owner's own verified log. `checkResolutionHead` in `sdk/src/foundation/person-authentication.ts` is the rule, and `signPersonOperation` takes a required third argument `held` and applies it. `spec/vectors/identity-log.json` gains a `signing` section with 6 cases (2 sign, 4 refuse); the earlier vectors are unchanged. `sdk/tests/foundation/identity-hostile-resolver-lockin.test.ts` replaces gap test #84: the poisoning resolution is refused, the checkpoint stays, the escape push is `advanced`, the new resolver authenticates and the former is refused. Documented in `identity-contract.md`, `person-authentication.md` and `identity-log.md`. Local suite on Node 22.23.2: 126 default, 198 v0.4/profile/interop/release, 323 foundation, typecheck clean. Builders: `signPersonOperation` changes signature, and a wallet built without it must apply the same rule. Still open: option 2 after #67, which makes resolution-only advances provisional and covers a stolen operational quorum plus a hostile resolver; F9 gate evidence needs a re-run, because `person-authentication.ts` and its tests are F9 inputs.

## October 22: Core-1, the minimal profile, and its envelope

[`spec/core-1/README.md`](spec/core-1/README.md) is a proposal the owner accepted in direction: the least two parties who have never met need to create identities and exchange a signed record each can verify offline. I-JSON with names that need no escape and integer-only numbers; SHA-256, strict Ed25519 and one encoding each for keys, signatures and time; one signed envelope `{body, signatures}` over `{domain, body}` with permanent domains; the foundation person and organisation identities and portable logs; signed records and offline-verifiable exchange bundles. Everything else becomes an optional extension. Its first two steps merged the same day:

- **I-JSON** ([#91](https://github.com/runquik/direct-trade-protocol/pull/91)). The pre-parse guard refuses an object that names a member twice with `duplicate_member_name`, and `canonicalize()` refuses a member name with a quotation mark, a reverse solidus or a control character, so a producer cannot sign what a receiver refuses. `unsafe-json.json` gains 5 refusals and 4 acceptances, each refusal names its code, and `canonicalization.json` drops the cases a non-JavaScript implementation could not reproduce or that contradicted the member-name rule. Builders: a host now answers `400 duplicate_member_name` to text it accepted before.
- **Envelope** ([#93](https://github.com/runquik/direct-trade-protocol/pull/93)). `signEnvelope(domain, body, keys)` and `verifyEnvelope(domain, envelope)`: the verifier supplies the domain; any extra member, a key signing twice, a key id that is not a key, a domain without a format version, or one failing signature refuses the whole envelope. `CORE1_DOMAINS` lists the domains. `spec/core-1/vectors/envelope.json` reproduces byte for byte. Exported from the preview entries as `core1`; the stable entry is unchanged.

Also on October 22, `canonicalization.json` gained a case whose key order differs by UTF-16 code unit and by code point ([#79](https://github.com/runquik/direct-trade-protocol/issues/79)), so a canonicalizer sorting by code point now fails a published vector. The reference already sorted by code unit.

## October 6: a refused move can be escaped ([#64](https://github.com/runquik/direct-trade-protocol/issues/64))

A destination that attested a move and later refused it stranded the identity at every relying party that had already admitted the move: the party's checkpoint sat on top of the refused rehome, so every later log, a move away included, was refused as `refused-move`. The owner chose an escape rehome. A log containing a refused rehome is now admitted when a later rehome in it goes to another destination (resolver id and resolver key both differ from the refusing one's); that rehome is signed by the recovery quorum like every rehome and must be adopted by the next destination under the existing adoption-evidence rule (`unadopted-move` otherwise). Rehoming back to the refusing destination does not count. The rule lives in the shared judge, so `judgeIdentityLog`, `admitIdentityLog`, the push and both adapter paths apply it. `recordRehomeRefusal` also returns `contradicts_admitted_move`, true when the host's checkpoint already lies at or past the refused head: the pair is kept as equivocation evidence and the host SHOULD distrust that destination. `spec/vectors/identity-log.json` gains 6 admission and 1 push vectors and one published key (`resolver-c`); the earlier vectors are unchanged. A new adapter test shows a stranded person recovering. Still open: the owner's decision and merge, and gate evidence for F9 person-auth and the foundation identity vectors.

## October 6: snapshot import has conformance vectors ([#63](https://github.com/runquik/direct-trade-protocol/issues/63))

The host rules a destination re-runs when it imports a snapshot (packaging pins, product, order, forecast and party continuity, order genesis, the personnel rule for `person` parties, inventory replay) were pinned only by the reference's own tests, so an independent host could not check that it admits and refuses the same snapshots; #59 showed import is where implementations drift. The owner accepted whole snapshots, normative for v0.4. New `spec/vectors/snapshot-import.json` (generator `sdk/scripts/build-snapshot-import-vectors.ts`, `--check` idempotent): a base company with the five registered kinds that a destination MUST import, reproducing the listed heads and ledger exactly, and 10 cases that each break one rule with the affected commands re-signed by a published key, which it MUST refuse with `invalid_snapshot`. Both #59 cases are included. `spec/v0.4/SPEC.md` section 8 names the file as the conformance definition for import; `sdk/tests/v04/snapshot-import-vectors.test.ts` runs every case against the reference import and is the new `snapshot-import-vectors` check under release gate G06. No gate was marked; the G06 evidence needs a re-run. Still open: `inventory-v1` pools are not in the base (the five registered kinds are), and invoice and private-profile import rules have no vectors.
## October 5: a relying party honours a held rehome refusal ([#56](https://github.com/runquik/direct-trade-protocol/issues/56))

`identity-log.md` said a relying party holding a destination's refusal of a rehome MUST refuse any log containing it, but the judge took no refusals and the reference relying party could not store one. The owner chose to implement it. `judgeIdentityLog`, `admitIdentityLog` and the push lookup take the refusals a party holds, and a log containing a refused rehome is refused with the new normative reason `refused-move`, checked right after the identity. The authentication adapter gains the `person_auth_rehome_refusals` table and `recordRehomeRefusal(tx, …)`, which keeps a refusal only of a rehome in a log that verifies for the person (so nobody can fabricate refusals for someone else), at most 64 per person, and keeps both artifacts; both admission paths pass the stored refusals in, and the judge matches them by the digest they name. `spec/vectors/identity-log.json` gains 4 admission and 2 push vectors and a `refusals` member on every admission and push (empty for the earlier ones, which are otherwise unchanged). Still open: the owner's merge, and gate evidence for F9 person-auth and the foundation identity vectors.

## October 5: snapshot import re-checks inventory pack conversions ([#59](https://github.com/runquik/direct-trade-protocol/issues/59))

The red team showed that the live write path refused an `inventory-v2` fact whose pack conversion the product never published (`unknown_packaging`), but snapshot import replayed facts through the reducer alone, which trusts the wire `base_units_per_pack`. A destination therefore admitted a signed fact no live host would accept, and its rebuilt ledger held phantom stock. Import now applies the same host rule (`unpublishedPackaging`, shared by both paths) against the product revision that was head when the fact was recorded, and refuses the snapshot as `invalid_snapshot`. `spec/v0.4/SPEC.md` says so. Verified by `sdk/tests/v04/inventory2-snapshot-packaging.test.ts`, which replaces the red-team gap probe: the bogus conversion and a conversion pinned before the product published it are refused, a legitimately published later revision imports and reproduces the ledger. Still open: the owner's acceptance (the rule refuses snapshots earlier reference hosts accepted), and gate evidence that fingerprints `SPEC.md`.

## October 4: the `requested_by` rule is specified ([#54](https://github.com/runquik/direct-trade-protocol/issues/54))

`requested_by` decided personal authority and whether an installation call is interactive or autonomous, but the specification only showed it in an example: a client following the documents could send `null` for a person command and be refused without explanation, and a host could key the automation check off the installation record alone and let an interactive-only module act without a human. `spec/v0.4/SPEC.md` section 2 now defines it (person: equals `actor.id`; installation: `null` is autonomous and needs `mode` `"automation"` and a live sponsor, a person ID is interactive and needs that active member's signature), `command.schema.json` carries a description, and [`spec/vectors/requested-by.json`](spec/vectors/requested-by.json) gives 13 scenarios with their outcome and error code, checked by `sdk/tests/v04/requested-by.test.ts`. The reference already behaved this way; no outcome changes. Not covered by a vector: an automation installation whose sponsor has left the company.

## October 3: a retired recovery key can no longer outrank the owner ([#50](https://github.com/runquik/direct-trade-protocol/issues/50))

The red team showed that epoch precedence counted epochs only: a recovery key the owner had retired with `recovery-policy` could fork from an older head, rehome twice, and supersede the owner at every relying party, through an unauthenticated push. The owner chose a fork-point rule. `docs/foundation/identity-log.md` now says a higher-epoch branch supersedes only if the recovery quorum it forked under is still current at the other history's head; otherwise the pair is a conflict that fails closed. `precedence` applies it; `judgeIdentityLog`, `admitIdentityLog` and `receiveIdentityLogPush` take the relying party's pinned history (the log it holds, ending at its pin) and refuse a conflict against it before any other rule. A party holding only the pin refuses every conflict with its checkpoint, a higher-epoch one too. New vectors in `spec/vectors/identity-log.json` (2 precedence pairs, 6 admissions, 3 pushes, and the bare-pin supersede is now a conflict); the red-team gap test is replaced by `sdk/tests/foundation/identity-retired-recovery-fork.test.ts`, which fails on the previous code. Builders: pass your pinned history if you keep one; if you keep only a pin, a move that forks from your checkpoint is now refused, not admitted. Still open: the reference authentication adapter keeps only its checkpoint, so it no longer admits a superseding move; a party whose pin predates the `recovery-policy` admits the retired-key branch until it sees the owner's history; the adapter does not take in rehome refusals yet.

## October 2: health advertises the digests behind each protocol kind ([#42](https://github.com/runquik/direct-trade-protocol/issues/42))

`GET /dtp/v0.4/health` listed protocol kind names only, so a module could not see which contract a host's registry carried for a kind without the registry file. The owner chose the additive member: `capabilities.protocol_kind_digests` maps each kind to the sorted digests the host's registry lists for it; `protocol_kinds` is unchanged. The specification now says health is discovery only and a module verifies every digest against the contract it pins. New fixture `spec/v0.4/fixtures/health-capabilities.json` (regenerate with `node sdk/scripts/build-health-fixture.ts`), checked against a running host; the external-module example now stops if the host does not list a pinned digest under its kind, and never takes a digest from health. Builders: nothing to change; read the map if you want to check a host before calling `records.list`. ## October 2: small-order keys are refused at registration ([#47](https://github.com/runquik/direct-trade-protocol/issues/47))

The verification rule (#44) accepts small-order public keys, and the identity key "signs" every message, so its possession proof was no barrier: the reference let such a key found a person, be added by rotation, or enter a foundation identity's control. The owner approved refusing weak keys at registration rather than at verification. `spec/v0.4/SPEC.md` section 2 now requires a key that enters an identity or authority record to decode to a point of prime order (`person.register`, `person.rotate` additions, installation keys; foundation genesis, rotation, recovery and recovery-policy changes), refusing the eight small-order points, mixed-order points and non-canonical or off-curve encodings. New vectors `spec/vectors/key-registration.json` and helpers `keyOrder` / `registrableKey` in `sdk/src/keys.ts`; `sdk/tests/18_key_registration.test.ts` and `sdk/tests/foundation/identity-registry-keys.test.ts` fail without the checks, and assert that every key in the other vectors is registrable. Verification, snapshot import and identity-log verification are unchanged, so an existing record that holds such a key stays verifiable. Builders: run the vectors against your key-registration path. Mixed-order keys are refused too; the owner confirmed that choice on [#48](https://github.com/runquik/direct-trade-protocol/pull/48).

## October 2: Ed25519 verification is pinned ([#44](https://github.com/runquik/direct-trade-protocol/issues/44))

The specification said every signature must verify but not by which rule, and Ed25519 libraries disagree on malleated and edge-case signatures, so two honest hosts could disagree about a record (a host using a tweetnacl-style verifier accepts `S + L`). The owner approved strict verification. `spec/v0.4/SPEC.md` section 2 now requires RFC 8032 section 5.1.7, cofactorless, refusing `S >= L` and non-canonical encodings of A and R; small-order points are not refused by themselves. New vectors `spec/vectors/signature-verification.json` (the fixed key's signature with `S + L`, a non-canonical identity key, and the twelve *Taming the Many EdDSAs* cases); `sdk/tests/17_signature_verification.test.ts` fails if the reference gives any other outcome. `verifyBytes` now checks the encodings and `S` itself rather than relying on WebCrypto, and that found one gap: the reference accepted a non-canonical encoding of the public key A, and now refuses it. The red-team gap test `sdk/tests/fuzz/signing-malleability.test.ts` is retired in favour of the conformance test. Builders: if your verifier is not WebCrypto or another RFC 8032-strict library, run the vectors. Small-order public keys (a key that "signs" every message) are accepted by this rule; they are refused at key registration instead (see the entry above, [#47](https://github.com/runquik/direct-trade-protocol/issues/47)).

## October 1: inventory state keys are digests ([#38](https://github.com/runquik/direct-trade-protocol/issues/38))

v0.4 migration refused every organization that had recorded an inventory event: the host's `observations` (inventory-v1) and `facts` (inventory-v2) maps, and the v1 pool's observations, packaging and reservations, were keyed by `JSON.stringify` of the identity tuple, and the destination's safe parser refuses those member names. Still open: a host holding state in the old form must rebuild its projection from signed records; the reference host has no migration for that.

## Sprint 01: two-builder interop (historical)

Four candidate modules; each builder picks two. Success: sign up once; a stranger's module works without a conversation; a money decision from records alone; everyone sees the same truth; nobody saw or did what they were not allowed to; a gap list, not just a demo. See the sprint brief §4–6.

| Module | What it does |
|---|---|
| **Passport** | onboard a company once; manage keys; grant and revoke module access; a "my protocol state" view |
| **Trade Ledger** | buyer orders, seller ships and attests, buyer attests receipt |
| **Early Pay** | watches for attested deliveries, issues an invoice, offers an advance from records alone, records payout and payoff |
| **Books** | read-only: who owes whom, paid or overdue, full history, assembled from others' records |

Later candidates: Inventory (with manufacturing as lot transformation), Reputation (derived, cannot self-grade), Demand Plan, an aging-stock marketplace.

## The planned first module, Passport (historical)

Every module was to be a core library, an MCP surface and a minimal web page:

1. `modules/passport/`: a small TypeScript package on `sdk/` (`DtpStoreClient`, `draft`, `signRecord`, `generateKeyPair`), pure functions, no UI dependencies: `onboardCompany`, `addKey` / `revokeKey`, `grantModule` / `revokeGrant`, and `myState`, which lists everything visible about the company. Key custody for the sprint: a local encrypted-at-rest JSON file per company (mock KYB), logged as a gap.
2. An MCP server exposing those as tools.
3. A minimal web page (plain HTML and fetch) for the "my protocol state" view, with grant and revoke buttons.
4. Tests against the development store (the `storeUnderTest()` pattern in `sdk/tests/helpers.ts`). Each module starts by reading `docs/PROTOCOL_STORE.md` cold and logging anything unclear in the gap log.
